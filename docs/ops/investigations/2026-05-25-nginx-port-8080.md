# Investigação — nginx.service Failed / Conflito na Porta 8080

**Data:** 2026-05-25 09:57
**Investigador:** Claude Code (sessão Roberto)
**Status:** ✅ Diagnóstico concluído — aguardando aprovação para resolução

---

## TL;DR

**Não é um nginx órfão.**
nginx é o reverse proxy de produção do NOC dashboard (`noc.grupogadens.com.br`), servindo tráfego HTTP/HTTPS real. O conflito na porta 8080 é uma **colisão permanente de design**: o `zabbix-mcp-server` foi instalado com a porta 8080 configurada como seu endpoint MCP HTTP transport, mas nginx já usa 8080 como seu servidor HTTP principal. Os dois serviços estavam em conflito **antes mesmo de hoje** — o `zabbix-mcp-server` acumulou **14.784 reinicializações** tentando ocupar a porta bloqueada pelo nginx.

Quando nginx foi parado durante o teste do guardrail `sysstop`, o `zabbix-mcp-server` finalmente conseguiu se ligar à 8080. Nginx não consegue mais iniciar por isso.

## 3. Configuração nginx ativa

**Arquivo principal:** `/etc/nginx/conf.d/noc.grupogadens.com.br.conf`

nginx está corretamente configurado como **reverse proxy de produção** com 3 servidores virtuais:

| Porta | Propósito |
|-------|-----------|
| `8080` | HTTP principal — proxy para Flask (`:8091`) + Zabbix UI (PHP-FPM via FastCGI) |
| `8443` | HTTPS alternativo (cert self-signed) — proxy para Flask |
| `443` | HTTPS produção (Let's Encrypt `noc.grupogadens.com.br`) |

O bloco `:8080` serve:
- `/` → Flask app (`:8091`)
- `/dashboard/`, `/governanca/` → Flask app (`:8091`)
- `/zabbix/` → Zabbix UI via PHP-FPM (unix socket)
- `/api_jsonrpc.php` → proxy para si mesmo em `/zabbix/api_jsonrpc.php` (path rewrite)
- `/m365data/` → arquivos JSON estáticos em `/var/www/m365data/`
- `/legacy/` → HTML estático antigo

**Sites-enabled:** vazio (nenhum site habilitado via symlink — toda config está em `conf.d/`)

⚠️ **Bug de auto-referência:** O bloco em `:8080` tem:
```nginx
location = /api_jsonrpc.php {
    proxy_pass http://127.0.0.1:8080/zabbix/api_jsonrpc.php;
```
nginx na porta 8080 faz proxy para si mesmo na porta 8080 — funcionava porque a
rota de destino é `/zabbix/api_jsonrpc.php` (diferente do trigger `/api_jsonrpc.php`).
Tecnicamente funcional mas confuso e frágil.

## 7. Classificação do Cenário

**Não é Cenário A** (nginx órfão) — nginx serve produção real (HTTPS 443, Zabbix UI, NOC).
**Não é Cenário B** (proxy mal configurado) — nginx está corretamente configurado.
**É Cenário C+ — Conflito de Design Permanente:**

O `zabbix-mcp-server` foi instalado configurado para usar porta 8080 como MCP HTTP
transport, mas essa porta já pertencia ao nginx de produção. O serviço estava
crashando e reiniciando a cada ~5 segundos há semanas (14.784 tentativas).

```
Chronologia do problema:
  [instalação do zabbix-mcp-server]
         ↓
  zabbix-mcp-server tenta :8080 → nginx bloqueia → crash → restart → repeat ×14784
         ↓
  2026-05-25 09:57 — nginx parado pelo guardrail test
         ↓
  zabbix-mcp-server finalmente ocupa :8080 e :9090 com sucesso
         ↓
  nginx não consegue mais iniciar
```

## 8. Análise Técnica

### Por que o zabbix-mcp-server quer porta 8080?

O `zabbix-mcp-server` (github.com/initMAX/zabbix-mcp-server) expõe:
- Porta **9090**: admin web portal (configuração, status)
- Porta **8080**: MCP HTTP transport (endpoint que Claude Desktop usa para fazer tool calls)

O config em `/etc/zabbix-mcp/config.toml` (leitura negada — pertence ao user `zabbix-mcp`)
provavelmente contém algo como:
```toml
[server]
host = "127.0.0.1"
port = 8080

[admin]
host = "127.0.0.1"
port = 9090
```

### Por que isso nunca foi percebido?

Enquanto nginx estava rodando, o zabbix-mcp-server falhava silenciosamente (exit code 1)
e era reiniciado a cada 5s. Sem alerta no healthcheck, sem impacto visível (9090 ficava
UP por ~5s antes do crash no bind :8080). O sistema parecia "funcionar" porque a API
Zabbix era servida pelo nginx.

### O bug de auto-referência no nginx (baixa prioridade)

O bloco `location = /api_jsonrpc.php { proxy_pass http://127.0.0.1:8080/zabbix/... }` faz
nginx na :8080 proxiar para si mesmo na :8080 — um loop técnico. Funcionava porque o path
de destino é diferente, mas é um anti-padrão. A correção correta seria usar FastCGI diretamente
para o `/api_jsonrpc.php`, igual ao bloco `/zabbix/`.

## 9. Recomendação Técnica

**Resolução: alterar a porta do zabbix-mcp-server de 8080 para uma porta livre.**

Portas livres candidatas: **8082**, **8083**, **8888** (não em uso no servidor).

```bash
# Passos (requerem sudo — aguardando aprovação de Roberto):

# 1. Editar /etc/zabbix-mcp/config.toml: mudar port de 8080 para 8082
sudo sed -i 's/port = 8080/port = 8082/' /etc/zabbix-mcp/config.toml
# OU editar manualmente se o formato for diferente

# 2. Reiniciar zabbix-mcp-server
sudo systemctl restart zabbix-mcp-server

# 3. Verificar que 8080 ficou livre
ss -tlnp | grep 8080   # deve retornar vazio

# 4. Iniciar nginx
sudo systemctl start nginx
sudo systemctl status nginx

# 5. Validar
curl -sS http://127.0.0.1:8080/api_jsonrpc.php -d '{"jsonrpc":"2.0","method":"apiinfo.version","params":{},"id":1}'
curl -sS -o /dev/null -w "%{http_code}" http://127.0.0.1:8080/zabbix/

# 6. Atualizar Claude Desktop MCP config para apontar para :8082
# (arquivo em ~/.config/claude/claude_desktop_config.json ou similar)
```

**Alternativa (mais simples se o formato do config não for trivial):**
Usar a variável de ambiente para override de porta no systemd unit:
```ini
# sudo systemctl edit zabbix-mcp-server
[Service]
Environment="ZBX_MCP_PORT=8082"
```
